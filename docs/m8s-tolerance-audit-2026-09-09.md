# M8S 傷害容許區間調查（2026-09-09）

本文件保存調查當時的樣本與結論。後續已依使用者指示在工作區實作「機制校正後 ±10,000」，尚未發布或執行正式資料回補；現行設定與操作以 [設定說明](../config/README.md) 及 [資料管線](data-pipeline.md) 為準。調查及本機驗證均未改寫排行榜、檢查點或歷史傷害。

## 建議

**優先修正預期傷害，再容許 ±10,000。** M8S 兩隻狼的玩家承傷基準不應永遠固定為最大 HP 的 40%；應按每場機制實際扣除的 HP 計算：

```text
每隻狼的預期玩家傷害 = 最大 HP − 該狼三次機制的實際有效傷害
容許區間 = 此預期值 ±10,000
整場預期傷害 = P1 固定 HP + P2 固定 HP + 兩隻狼各自的預期玩家傷害
整場容許區間 = 整場預期傷害 ±10,000（獨立檢查，不累加成 ±20,000）
```

P1／P2 的逐目標容許值維持 ±100，最大 HP、目標清單、普攻與同場多來源異常傳播規則繼續獨立檢查。此方案已在工作區實作；事件不完整或機制傷害本身不符預期時，不能直接採用上述公式放行。

**若暫時仍採用固定 40% 基準，建議的過渡區間為 −10,000～+300,000。** 對應每隻狼 `4,197,375～4,507,375`，整場 `148,739,091～149,049,091`，上下界均含。此區間能涵蓋目前觀察到的機制差異，但仍可能放過區間內未被其他檢查抓到的錯誤傷害；未來更大的正常機制過量擊殺也可能超出上界。現行逐目標設定只支援對稱 `damage_tolerance`，非對稱區間需要擴充判定與邊界測試，不能只填一個設定數字。

−10,000 的依據是機制校正後每隻狼最小殘差 −8,134、整場最小殘差 −8,183；+300,000 則是在已確認的最大機制過量擊殺 252,176 之上保留約 19% 空間。兩者都是依本次樣本提出的實務邊界，不能宣稱為統計上唯一最佳值。對稱 ±100,000 會放寬未觀察到需求的負向區間，卻仍擋住已能用機制解釋的正向偏差。

## 資料與方法

- 母體：Data repo [固定快照 7583e958](https://github.com/Kantai235/Final-Fantasy-XIV-Ranking-for-TC-Data/tree/7583e9586eb955a82acf89dad7814f1354ae7f03)，`data/rankings/savage_m8s.reports/000.json` 內 1,192 份報告、1,244 筆 report/fight 上傳量測。
- 依既有 v2 戰鬥身分契約分成 645 組，其中 37 組含被完整性規則隱藏的來源。玩家名單缺漏或身分欄位差異仍可能讓同場分在不同組，因此不把 645 宣稱為完全準確的實際通關場數。
- 優先抽查每組被隱藏且偏差最大的來源，另取 5 份目前未隱藏的對照。抽查查詢另避免開戰時間與總承傷完全相同的重複來源，僅節省 API 額度，不修改正式去重契約。
- 選出 40 份樣本。原來源有 36 份可讀；其中 3 份不可讀者改查開戰時間與總承傷相同的另一份上傳作機制對照，最終 39 份取得完整六次機制傷害，1 份仍不可讀。對照來源可證明該場的機制行為，不等同確認原不可讀報告目前的公開資格。
- 使用既有 `fetch_fflogs.py` 的認證、GraphQL 與例外處理方法唯讀查詢。先核對 Target Damage，再查 `events(dataType: All, includeResources: true)`，限制 `fightIDs` 及該 fight 起點後 190,000～250,000 ms 的機制窗口，完整處理分頁；每隻狼都需實際取得三次機制。
- 僅加總 `type="damage"` 的有效 `amount`，不重複計入 `calculateddamage`。以 fight 的 NPC gameID 對應狼與機制來源；只保存技能／目標彙總，不保存原始事件、玩家名稱、sourceID 或憑證。

本次是針對被擋紀錄的原因調查，不是隨機抽樣；不能用樣本通過比例推估全站誤判率。機器可讀證據見 [彙總 JSON](m8s-tolerance-audit-2026-09-09.json)。

## 為何固定 40% 會偏高

風狼與石狼的最大 HP 都是 10,518,438。查核樣本顯示，每隻狼會承受三次 `Wind Surge`／`Sand Surge`，一般每次名義傷害為 2,103,687，合計 6,311,061。最後一次機制若造成過量擊殺，只會實際扣除剩餘 HP，因此玩家可以合理打出超過固定 40% 的累積傷害。

一般沒有機制過量擊殺時，預期玩家傷害為 `10,518,438 − 6,311,061 = 4,207,377`。舊規則將 40% 四捨五入為 4,207,375，兩者本來就有 2 點取整差異。

| 證據案例 | 舊 40% 基準的狼傷害偏差 | 機制過量擊殺 | 改按實際機制承傷計算後的殘差 |
| --- | ---: | ---: | ---: |
| [原回報，fight 9 風狼](https://www.fflogs.com/reports/9MKXTFhcZ4NC8JRp?fight=9) | −7,276 | 0 | −7,278 |
| [G26DHJmAYhzPn8vM，fight 5 石狼](https://www.fflogs.com/reports/G26DHJmAYhzPn8vM?fight=5) | +99,366 | 99,365 | −1 |
| [czxDR3Cap2wYX7Td，fight 2 石狼](https://www.fflogs.com/reports/czxDR3Cap2wYX7Td?fight=2) | +252,178 | 252,176 | 0 |

最後一例的第三次機制有效傷害只有 1,851,511：`2,103,687 − 1,851,511 = 252,176`。按實際機制重算，預期玩家傷害就是 FFLogs 記錄的 4,459,553，完全吻合；±100,000 仍會誤擋這種機制情況。

39 份可讀樣本中，29 份一般正向偏差案例的狼殘差全部落在 −2～0；排除下面的明顯異常案例後，38 份樣本的全部狼殘差介於 −8,134～0，整場殘差介於 −8,183～−25。四份負向案例的小幅差額尚未確認成因，不應直接宣稱是漏封包或上傳錯誤。

## 異常仍需辨識

另查得 [Xzgfb8qGyP924jFM，fight 62](https://www.fflogs.com/reports/Xzgfb8qGyP924jFM?fight=62) 整場較固定基準高 2,775,315，且 P1／P2 分別偏高 978,157／1,595,771。即使使用實際機制承傷重算，風狼仍多 332,051、石狼仍多 142,092，不能由機制過量擊殺解釋。

該案例每隻狼的機制有效傷害加過量擊殺為 6,447,441，也高於一般樣本的 6,311,061。正式實作必須同時核對機制來源、技能、次數，以及每次有效傷害加過量擊殺是否符合名義傷害；不能將任何讀到的敵方傷害都當成正確基準。此處的「異常」描述的是資料不一致，不推斷玩家行為。

本次觀察到的機制來源 NPC GUID 為 18261、18262，技能 ID 為 41965、41966、43137、43138、43520；它們是本次觀測集合，正式判定仍須核對 M8S、副本版本、目標 GUID 與最大 HP，避免套用到其他內容。

## 後續實作邊界

採用機制校正方案時，只在 Python 抓取／完整性層計算與保存版本化摘要；不把原始事件寫入 Data repo，也不讓 Node 或 Vue 重新呼叫 FFLogs。需為 M8S 更新 profile／證據版本，讓既有回補器補查缺少機制摘要的來源；舊 Target Damage 快取本身不足以推算機制過量擊殺，不能宣稱可全部離線重判。

驗證應涵蓋過量擊殺、無過量擊殺、少量負向殘差、明顯異常、缺少機制事件、錯誤技能／來源、取整差異、±10,000 邊界及多來源重判。完成所有同場來源的重判後，再由既有建置流程更新公開資格，仍須遵守 hydrate 與 append-only 保護。
